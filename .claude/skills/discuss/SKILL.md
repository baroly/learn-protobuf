# 文件討論規範

使用者讀文件時，把想法直接寫在文件裡；Claude 讀出這些標記，把回覆寫進討論檔；使用者在討論檔最後面接著回；Claude 再接在後面寫下一輪。

**討論的載體是文件，不是對話。** 兩個方向都是：

| 方向 | 載體 | 理由 |
|---|---|---|
| 使用者 → Claude | 文件裡的 `@ask` / `@but` 標記；之後是討論檔最後的回覆區 | 報告動輒數千字，在對話裡說「第三節那個欄位」很容易對錯地方；標記就寫在它針對的段落旁邊，指涉永遠精確 |
| Claude → 使用者 | `docs/template/discuss/` 的同名討論檔 | 回覆同樣動輒數千字，在終端機裡滾動讀很痛苦，而且對話一長就往上捲不回去。寫成 MD 檔可以用編輯器讀、可以搜尋、可以慢慢回 |

**對話視窗只留一兩行交代。** 使用者要在 CLI 裡打長回覆時，很容易一個 Enter 就把沒寫完的訊息送出去 —— 所以回覆也寫在檔案裡，兩邊都用同一個載體。

適用的文件：`docs/plans/` 的報告、kickoff 階段的 `docs/architecture.md` 與訪談檔，以及任何使用者要求「看我的標記」的文件。

---

## 三個標籤

| 標籤 | 寫在哪 | 意思 | Claude 該做什麼 |
|---|---|---|---|
| `@ask` | 文件裡（或回覆區） | 我不懂，解釋給我聽 | **只解釋。** 不改文件、不動程式碼、不提議動工 |
| `@but` | 同上 | 我有不同想法，這裡要討論 | **先判斷對錯再回應。** 不是收到反對就照做 |
| `@resp <編號>` | **討論檔最後一輪的回覆區** | 我對第 N 則議題的回覆 | 在下一輪接著回，照 `@ask` / `@but` 原本的性質繼續 |

前兩個標的是「我對文件有意見」，`@resp` 標的是「我對你的回覆有回應」—— **三個都是行首前綴，一次 grep 全抓得到。**

`@resp` 為什麼值得多一個標籤：回覆時使用者不必再判斷「這算問還是算反對」。
少一個打字前的決定，就少一個「懶得標」的理由 —— 這跟標籤用小寫英文是同一個考量。

另外還有一個**只有 Claude 會寫**的標記：每一輪開頭的 `## @round N · 日期`。它不是給使用者用的，是用來切分「哪些已經處理過」，見下面「討論檔的結構」。

### 為什麼是英文

全小寫 ASCII，不用切輸入法、不用按 shift。標記是寫在中文段落中間的東西，如果連標籤都要切輸入法，就會懶得標。

## 怎麼寫標記

**行首前綴。** 標籤獨立起一行的開頭，後面接內容，可以跨多行：

```markdown
### 狀態欄位

status: draft | published | archived

@but 這裡只留三個狀態會不會太省？
我想加 scheduled（排程發布），
反正現在加是免費的

### 發布流程
```

標籤**獨立成一行**也可以，內容從下一行開始 —— 想法比較長的時候這樣寫更順手：

```markdown
@ask
我剛剛查了一下資料，說是如果未來要支援多語系，
可能會需要下面這些欄位，幫我評估：
1. ……
2. ……
```

兩種寫法等價，看當下順手。

### 三條規則

| 規則 | 說明 |
|---|---|
| **一個空行結束一則標記** | 從標籤行開始，到下一個空行為止都算同一則。要寫兩件事就開兩則標記 |
| **標記緊貼在它針對的段落下方** | 針對整份文件的意見放在最上方、標題底下。`@resp` 例外 —— 它靠編號指涉，寫在討論檔最後一輪的回覆區 |
| **標籤必須在行首** | 行首才 grep 得到。寫在句子中間的 `@but` 不算標記 |

## 討論檔放哪

### 位置與命名

**與原文件同名、同子目錄，放在 `docs/template/discuss/` 底下：**

```
docs/plans/phase 1/000007 - 好友.md            ← 報告（進版控）
docs/template/discuss/phase 1/000007 - 好友.md ← 討論檔（不進版控）

docs/architecture.md                           ← kickoff 階段的方向草稿
docs/template/discuss/kickoff/architecture.md  ← 它的討論檔
```

**階段子目錄兩邊要一致。** 報告放哪個階段，討論檔就放同名的階段目錄 —— 配對靠「同路徑同檔名」，
少了階段那一層就可能出現兩個同名檔而配不起來。

第一次要開討論檔時，複製 `.claude/skills/discuss/template.md` 的骨架，把欄位填上。

### ★ 這個資料夾不進版控

`docs/template/` 在 `.gitignore` 裡，是「交流用暫存空間」。所以：

| | |
|---|---|
| **好處** | 討論過程不會汙染 git 歷史，寫多長都沒關係，不必字字斟酌 |
| **代價** | **討論檔隨時可能消失，它不是紀錄。** 收斂出來的決定一定要寫回原文件正文（必要時追加 `docs/decisions.md`），否則結論會跟著檔案一起蒸發 |

不要 commit 討論檔，也不要為了保存它而把它移出 `docs/template/`。

---

## ★ 討論檔的結構：一輪一個區塊，只往下長

**討論檔是照時間順序往下寫的紀錄。** 每一輪是一個區塊，接在檔案最後面；**寫過的輪次一個字都不再動** —— 不回頭補、不改狀態、不搬使用者的字。

```markdown
## @round 1 · 2026-10-05

### 1 · @but 狀態欄位太少 —— 第二節
> 使用者在報告裡寫的標記，逐字引用
（Claude 的回覆）
**狀態**：等回覆

### 2 · @ask …

### 待收斂
| # | 主題 | 卡在哪 |

### 回覆
@resp 1
（使用者的回覆 —— 放著不動）

## @round 2 · 2026-10-06

### 1 · @but 狀態欄位太少
（直接接著回，不再引用上面的字）
**狀態**：已收斂 —— 結論：…，已寫回第二節

### 待收斂
…

### 回覆
（使用者下一輪寫在這裡）
```

### 為什麼這樣排

| 原因 | 說明 |
|---|---|
| **使用者只讀內文、從上往下讀** | 新的東西永遠在最下面，不必回頭找哪裡改過 |
| **使用者是讀完才一次回完的** | 回覆集中在該輪最後，不必每回一條就往上滑到對應的段落 —— 規範打不贏習慣 |
| **Claude 靠 `@round` 切出「還沒處理的」** | 最後一個 `## @round` 之後的使用者文字就是新的；之前的全部處理過了，不必再判斷 |

代價是**同一個議題的來回會散在好幾輪裡**。補償方式是每一輪最後的「待收斂」表 —— 最新的整體狀態永遠在檔案最底下。

### 每一輪的寫法

| 規則 | 說明 |
|---|---|
| **開頭 `## @round N · YYYY-MM-DD`** | N 從 1 起逐輪加一；同一天多輪也是靠 N 區分，日期只是參考 |
| **議題標題 `### <編號> · <標籤> <主題>`** | 第一次出現時加 `—— <在原文件的哪一節>` |
| **議題編號跨輪固定** | 第 3 號在每一輪都叫第 3 號；新議題接著往下編。使用者的 `@resp 3` 靠它指涉，**給出去就不能改** |
| **只列本輪要回的議題** | 已收斂的議題，後面的輪次不再列出 |
| **每則最後一行 `**狀態**`** | `等回覆` 或 `已收斂 —— 結論：<一句話>，已寫回第 X 節` |
| **每輪最後是「待收斂」表，再來是空的「回覆」區** | 「待收斂」列出所有還沒結的議題，包含這一輪沒動到的 |

### 引用的規則

- **第一次出現的標記要逐字引用**（`>` 引言）—— 它在另一份文件裡，不引用就對不上
- **使用者在回覆區寫的字不引用**，就在正上方，讀得到。一則回覆裡有好幾點時，可以**短短引用正在回的那一句**，只為了對得上
- 引用永遠是複製，**不搬動、不改寫**使用者的字

### 找出要回的東西

兩個來源，一起看：

```bash
f="docs/template/discuss/phase 1/000007 - 好友.md"
doc="docs/plans/phase 1/000007 - 好友.md"

# 1. 討論檔：最後一個 @round 之後的使用者文字
last=$(grep -n "^## @round " "$f" | tail -1 | cut -d: -f1)
tail -n +"${last:-1}" "$f" | grep -nE "^@(ask|but|resp)( |$)"

# 2. 原文件裡的標記（還沒被引用成議題的就是新的）
grep -nE "^@(ask|but)( |$)" "$doc"
```

**結尾的 `( |$)` 不可以省。** 少了它會連說明文字裡提到標籤的行一起抓；而如果反過來寫成要求標籤後面一定要有空格，「標籤獨立一行」的寫法就完全抓不到 —— **而且失敗是靜默的**：grep 回傳空的，看起來就像使用者根本沒標任何東西。

Claude 自己寫的東西不會被抓到：議題標題是 `###` 開頭，引用的標記前面有 `>`。

★ **grep 零結果不代表使用者沒回覆。** 他可能忘了打標籤、可能直接寫成 `1.` `2.` 的編號清單。
**最後一輪「回覆」區底下的所有文字一律算使用者的新回覆**，有沒有標籤都要讀，照編號或內容對回議題 —— 不要回他「我沒看到你的回覆」。

原文件裡的標記：判斷「回過了沒」看討論檔裡有沒有逐字引用它。被引用之後**原地留著不要動**，直到收斂（見「什麼時候才能刪標記」）。使用者之後在原文件加的新標記，下一輪開成新的議題編號。

**不屬於任何議題的事，`@resp` 不帶編號就好**（`@resp 0` 也算）。使用者不該為了「這該算第幾則」而卡住。

### 對話視窗只留交代

寫完一輪，在對話裡只講這些，**不要把回覆內容再貼一次**：

```
第 2 輪寫好了：docs/template/discuss/phase 1/000007 - 好友.md
六則都回了，其中兩則我認為你的意見成立（議題 2、5）。
四則等你回覆，寫在檔案最後的回覆區就好。
```

使用者要的是「去哪讀、有幾條、有沒有我該特別注意的」，不是在終端機裡再讀一遍。

## Claude 怎麼回覆

### 一次回完，不要回一條就停

讀到標記後，**逐條回覆全部要回的東西，寫成一整輪，然後才停下來**。不要回完第一條就問「要繼續看下一條嗎」—— 使用者標了六條就是要六條的回覆。

依標記出現的順序回，不重排、不合併相近的兩條。使用者是照著讀的順序標的，那個順序本身有意義。

### `@ask` —— 只解釋

回答問題，就這樣。**不要順手提議改動、不要開始寫程式、不要產報告。** 使用者問「為什麼這兩個功能共用一張表」，他要的是理解，不是一份重構計畫。

解釋完如果確實發現文件有錯，說出來，但停在「這裡寫錯了」，不要直接動手。

### `@but` —— 先判斷，再回應

**這是整份規範最重要的一條。`@but` 是討論的開場，不是指令。**

收到反對意見時，先問自己「他說的對不對」，分三種情況：

| 判斷 | 怎麼回 |
|---|---|
| **他對** | 直接說他對，講清楚要改哪些地方、影響範圍多大，然後問要不要改 |
| **他錯** | 直接說哪裡不成立，給出理由或證據。**不要因為對方是使用者就讓步** |
| **各有道理** | 講清楚取捨，給一個推薦與推薦的理由。不要列完選項就丟回去讓他選 |

反例 —— 這是最該避免的回應：

```
@but 我覺得權限應該用關聯表比較好

好的，你說得有道理，我改成關聯表。
```

如果報告裡已經寫明選位元遮罩是為了避開熱路徑上的 join，而使用者的理由沒有推翻那個考量，正確的回應是把那個考量講出來，而不是撤掉它。**使用者要的是評估，不是附和** —— 會附和的話他自己想就好了，不需要問。

反過來說，使用者提出的理由如果真的推翻了原設計，就乾脆承認，不要為了維護原方案而硬拗。

寫在檔案裡不改變這一條。**版面變寬不是拿來把話說軟的** —— 能寫長，是為了把理由與證據寫清楚，不是為了鋪陳客套。

## 討論收斂之後

### 結論寫回原文件正文

達成共識後，把**決定**寫進原文件正文，刪掉該則標記，並在**下一輪**裡把那則議題的狀態寫成
`已收斂 —— 結論：<一句話>，已寫回第 X 節`。之前輪次裡的「等回覆」不回頭改 —— 最新一輪就是現況。

寫回去的是決定與理由，不是對話逐字稿。文件是給之後的人讀的，他要看的是「最後決定用位元遮罩，因為權限計算在熱路徑上」，不是「使用者問了、Claude 答了、使用者同意了」。

討論檔不進版控，**所以「寫回」不是收尾的儀式，是唯一一次把結論留下來的機會。**

### 什麼時候才能刪標記

**使用者明確表示接受，才能寫回並刪除。** 「嗯」「了解」「原來如此」都不算 —— 那是聽懂了，不是拍板。

**不要憑自己判斷討論已經收斂就去刪掉使用者寫的字。** 標記是使用者的東西，動它要經過他。

不確定時就留著，狀態保持 `等回覆`，並在對話那一兩行裡問「這幾條可以結了嗎」。

### 偏離原設計就記進 decisions.md

如果討論的結論改變了 `docs/architecture.md` 或原報告裡的決策，依 `CLAUDE.md` 追加到 `docs/decisions.md`。**追加，不覆寫。**
（kickoff 階段例外：方向還沒核准，談不上偏離，直接改 `architecture.md` 就好。）

---

## 討論不等於核准

`@but` 討論出「應該改成 X」之後，**不能直接開工**。

`CLAUDE.md` 的「先報告後動工」照常適用：

```
標記討論 → 結論 → 更新報告 → 等核准 → 才動工
```

討論階段產出的是共識，不是核准。如果結論讓報告的範圍變了，就把報告改到反映新範圍，然後再問一次。**討論熱絡不代表可以跳過那道門。**

## 禁忌

| 不要 | 為什麼 |
|---|---|
| 把逐條回覆貼在對話視窗裡 | 那是要在檔案裡讀的。對話裡只留「寫好了、在哪、幾條、幾條等回覆」 |
| 修改之前的輪次（補字、改狀態、刪段落） | 討論檔只往下長。現況寫在最新一輪 |
| 把使用者的回覆搬進議題裡 | 他的字留在原本的回覆區 |
| commit 討論檔，或把它移出 `docs/template/` | 那個資料夾刻意不進版控。要留下來的是寫回原文件的結論 |
| 只寫進討論檔就當事情辦完 | 討論檔會消失。結論沒寫回原文件等於沒發生 |
| 把標記當 TODO 自己去做 | 標記是意見，不是工單。`@but` 尤其不是 |
| 改動標記以外的地方 | 使用者標了三處，就處理那三處。順手整理別的地方會讓 diff 對不起來 |
| 修改或搬動使用者寫的標記文字 | 那是他的字。要引用就逐字引用，不要改寫 |
| 為了讓對話順利而同意 | 見上面 `@but` 那節。附和沒有價值 |
| 回一條就停下來等 | 使用者標完六條才叫你看，他要的是六條的回覆 |
| 把討論結論直接當成核准去動工 | 見「討論不等於核准」 |

## 標記與版控

| 東西 | 進版控？ | 怎麼處理 |
|---|---|---|
| 文件裡未結的標記 | **可以 commit** | 它是討論的中間狀態，留著比弄丟好，跨工作階段也接得回來。commit 訊息裡要說明這次帶進了討論標記 |
| 討論檔 | **不進版控** | `docs/template/` 已在 `.gitignore`，不必另外處理，也不要嘗試繞過 |
| 收斂後的結論 | **一定要 commit** | 寫回原文件正文，必要時追加 `docs/decisions.md` |

結掉之後記得把文件裡的標記清乾淨，不要讓已經定案的意見留在文件裡誤導之後的人。
