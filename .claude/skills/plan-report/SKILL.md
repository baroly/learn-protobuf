# 開工前報告

`CLAUDE.md` 規定了**什麼時候**要寫報告；這份規定**怎麼寫**。骨架在 `template.md`。

報告的讀者是要做決定的使用者。**目標是讓他能真的參與決策，而不只是按核准。**
所以重點不是「我要做什麼」，而是「有哪些決定、我推薦哪個、為什麼、推翻的話代價多大」。

---

## 檔名、位置、編號

```
docs/plans/phase 1/000001 - Phase 1 任務拆解.md
docs/plans/phase 1/000002 - 認證與裝置.md
docs/plans/phase 2/000013 - ….md
```

| 規則 | 理由 |
|---|---|
| 「六位流水號 + 空格 + 連字號 + 空格 + 功能名稱」 | 排序穩定、一眼看出順序 |
| **按階段分子目錄，流水號跨階段連續** | 一個編號只會有一份報告，引用時不必知道它在哪個階段 |
| **不重用號碼**，作廢的也不重用 | 被否決本身也是要留存的紀錄 |
| 一份報告的子計畫用 `000003-1` | 例如某一步的壓測執行計畫，太長不適合塞進母報告 |
| **其他地方引用只寫編號**（`見 docs/plans/000004 第一節`），程式註解尤其如此 | 報告歸檔到哪個階段是事後整理，註解不該因為整理而全部重寫 |

不是報告的東西（架構圖、參考資料）可以放在階段目錄裡，但**不給流水號**。

## 章節

### 檔頭

```markdown
# 000025 - 私訊聊天窗

**狀態**：待核准
**日期**：2026-10-01
**前置**：`000024` 已完成（…）。

（一段話：這份做什麼。）

做完之後：（從使用者角度描述做完的樣子 —— A 做了什麼、B 看到什麼。）
```

「做完之後」那段很重要：它是使用者判斷「這是不是我要的」最快的方式，也是驗收的依據。

### 零、先定結構問題（有就寫，放最前面）

這份報告裡**影響結構、推翻代價高**的決定，每一個獨立一小節，標題用 `★` 標出最重要的。
寫：問題是什麼、選了什麼、為什麼、它連帶影響什麼。

放最前面是因為：使用者時間有限時，**只讀第零節就要能抓到所有該他拍板的事**。後面的檔案清單是執行細節。

### 一、要改哪些檔案、各改什麼（必備）

按模組或層分組，每一項標**新增／改寫／刪除**。要指回第零節的哪一項。

### 二、對既有功能的衝擊與破壞性風險（必備）

- 會不會弄壞現有的東西
- 有沒有資料遷移、要不要重建資料庫、會清掉什麼資料
- 舊客戶端／已部署的服務會不會不相容；**部署順序**有沒有限制
- `### 已知風險`：做了之後可能出的問題與緩解方式

**沒有衝擊也要寫「沒有」並說明為什麼** —— 空著的章節看不出是「沒有」還是「沒想過」。

### 三、替代方案與取捨（必備）

每個決定一小節：`### A. 方案甲（★ 建議） vs 方案乙 vs 方案丙`，然後說每個方案的代價與排除的理由。

- **一定要有推薦。** 列完選項丟回去讓使用者自己選，是把思考工作推回去
- 使用者已經定案的寫 `（★ 使用者 <日期> 定案）`，不再重新論證
- 排除的方案也要寫出來：使用者可能正好想到那個，看到「已考慮過、因為 X 排除」就不用再問

### 四、步驟拆解與驗證方式（必備）

| # | 做什麼 | 怎麼確認沒壞 |
|---|---|---|

- **每一步一個 commit**，所以每一步都要是能建置通過的狀態
- 「怎麼確認沒壞」要具體：哪個指令綠、哪支腳本、檢查表第幾項
- **檢查表（人看畫面）**：UI 不寫測試，改成編號的檢查表 —— 做什麼、應該看到什麼。做完逐項走過，結果寫進第七節
- **哪些東西要有測試**：一張表，依 `CLAUDE.md` 的風險判準說明每一項要或不要、為什麼。不確定的在這裡問
- **只有手動驗過的**：先說清楚哪些不會有自動化驗證
- **預估**：天數，按步驟拆

### 五、不在本任務範圍

明確列出「看起來相關、但這份不做」的東西，以及它們在哪一份、哪一階段做。
這一節擋住的是**執行中的範圍蔓延** —— 做到一半「順手」加的東西沒有經過評估。

### 六、我自己決定、核准時可以推翻的

| 決定 | 推翻的話怎麼改 |
|---|---|

細節層級的決定（常數、文案、預設值、小的行為選擇）不值得各開一節討論，但使用者應該看得到。
寫出「推翻的代價」讓他知道哪些可以放心交給你、哪些值得多看一眼。

### 七、結果（完成後追加）

做完後**追加**到同一份報告，不另開檔案：

- 每一步的實際結果；量到的數字
- 檢查表逐項的結果
- **沒驗證到的東西，逐項明列**（例如「migration 未對真實資料庫執行」「多分頁情境只在 Chrome 試過」）
- 與報告原計畫不同的地方（同時追加 `docs/decisions.md`）

## 規劃型報告（階段任務拆解）

每個階段開始時先寫一份，例如 `000013 - Phase 2 任務拆解`。**它本身不實作任何東西**，核准的是「怎麼切」。

章節同樣是四項必備，但內容不同：

| 章節 | 寫什麼 |
|---|---|
| 先對詞彙（有需要時） | 這個階段會出現的新名詞，在程式、文件、畫面上各叫什麼 |
| 零、現況盤點 | 這個階段要的東西**已經有多少**；缺口是什麼 |
| 一、拆成 N 份 | 每份一個預留編號、範圍、為什麼這樣切、順序與相依 |
| 三、替代方案 | 切法、順序、跨份的共同決定（元件庫、驗證方式…） |
| 四、步驟 | 每份的預估、每份的驗收標準 |

拆出來的每一份之後**各自寫報告、各自核准**。一次核准一份、做一份。

切的原則：每一份做完都要是**能展示、能驗證**的狀態；先做後面每份都會用到的地基；有東西可以測的先做。

## 狀態與索引

報告頂端的「狀態」與 `docs/plans/README.md` 索引表要同步：

```
待核准 → 已核准 → 進行中（步驟 N）→ 已完成（日期）：一句結果
                ↘ 作廢（日期）：原因，編號不重用
```

- 索引表一份一列：編號、任務、狀態。完成時把**最重要的結果數字**寫進狀態欄
- 作廢的用 `~~刪除線~~` 保留在原位
- 改了報告範圍（例如討論後縮小）就改報告正文，狀態維持「待核准」，再問一次

---

## 核准之後

依 `CLAUDE.md`「核准之後一路做到底」。補充：

- commit 訊息以編號開頭：`000025 step 3: per-account database, wire trackers; delete on logout`
- 最後一步做完：追加第七節、更新索引狀態、更新 `README.md` 的「接續前必讀」、有偏離就追加 `decisions.md`
- 總結時講：做了什麼、量到什麼、**沒驗證到什麼**

## 禁忌

| 不要 | 為什麼 |
|---|---|
| 沒有推薦的替代方案章節 | 使用者要的是評估，不是一張比較表 |
| 把結構性的決定埋在檔案清單裡 | 使用者只讀第零節時會漏掉 |
| 章節空著不寫「沒有」 | 看不出是沒有還是沒想過 |
| 驗證方式寫「測試通過」 | 要寫哪個測試、哪個指令、檢查表第幾項 |
| 完成後另開一份結果報告 | 結果追加在同一份的第七節，一個編號一條完整的線 |
| 重用作廢的編號 | 引用會指錯 |
| 寫好報告就順手開工 | 告訴使用者「報告產好了」，停下來 |
