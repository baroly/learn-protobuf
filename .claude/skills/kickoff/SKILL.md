# 方向確立（kickoff）

**產出只有一個：一份狀態為「已核准」的 `docs/architecture.md`。** 在那之前不寫產品程式碼。

這一步跟之後的每一份報告是同一套邏輯，只是規模更大：
**先讓使用者評估，核准後才動工。** 差別在於這裡要核准的是「往哪裡走」，而不是「這一步怎麼做」。

---

## 為什麼要獨立一步

| 跳過它會怎樣 | 原因 |
|---|---|
| 做到一半發現規模估錯，整個架構要換 | 硬約束沒有量化，「要能撐很多人」不是約束 |
| 每一份報告都在重新爭論技術選型 | 選型沒有一個地方寫下理由，每次都得重來 |
| 做了一堆使用者根本沒打算要的功能 | 沒寫「不做什麼」 |
| 後來的人看不懂為什麼這樣設計 | 決策只活在某次對話裡 |

---

## 流程

```
盤點現況 → 訪談（一到三輪）→ 草擬 architecture.md（狀態：草稿）
       → @ask / @but 討論 → 收斂寫回 → 使用者核准（狀態：已核准）
       → 填 CLAUDE.md、建程式碼規範 → 第一份報告 000001 - Phase 1 任務拆解 → 等核准
```

### 1. 盤點現況

- **空專案**：直接進訪談
- **已有程式碼**（接手舊專案、或從雛形轉正）：先讀一遍，在訪談檔開頭寫「現況盤點」—— 有什麼、用什麼技術、哪些看起來是刻意的決定、哪些看起來是將就。**已存在的東西也是方向的一部分**，要嘛沿用、要嘛明說換掉

### 2. 訪談

把問題寫成檔案，不要在對話裡丟：`docs/template/discuss/kickoff/方向訪談.md`（不進版控）。理由同 `discuss` skill —— 回答動輒很長，在終端機裡打容易誤送。

| 規則 | 說明 |
|---|---|
| **一輪只問最關鍵的 5–8 題** | 題庫在 `questions.md`，挑跟這個專案有關、而且**答案會改變架構**的。一次丟 30 題，使用者會隨便答或乾脆不答 |
| **每題附上 Claude 的預設推薦與理由** | 使用者可以只回「照推薦」。沒有推薦的問題是把思考工作丟回去 |
| **題目編號固定** | 使用者在檔案最下面用 `@resp <編號>` 回，跟 `discuss` 一樣 |
| **答案不清楚就追問，不要自己補** | 「大概幾百人吧」要追問成「同時在線還是註冊數？一年後呢？」 |
| **使用者答「不知道」是有效答案** | 那就寫成「待驗證假設」，並說明要怎麼驗、在第幾階段驗 |

對話視窗只留一兩行：「訪談檔產好了：路徑。這輪 6 題，第 2、5 題最影響架構。」

通常兩輪就夠：第一輪問目標與約束，第二輪根據答案問技術取捨。

### 3. 草擬 `docs/architecture.md`

照 `docs/architecture.md` 骨架填，狀態寫「草稿」。必須包含：

| 章節 | 寫什麼 | 常見的錯 |
|---|---|---|
| **一句話定位** | 做什麼、給誰 | 寫成功能清單 |
| **硬約束** | **量化的**目標與天花板（規模、預算、硬體、時程、法規） | 「高效能」「可擴展」—— 沒有數字就不是約束 |
| **範圍：做 / 不做** | 第一階段做什麼；**明確不做什麼**，以及為什麼現在不做 | 只寫做什麼。「不做」才是擋住範圍蔓延的東西 |
| **架構決策** | 編號的決策（決策 1、2、3…），每條：選了什麼、**為什麼**、**排除了什麼**、什麼情況下要重新評估 | 只寫結論沒寫理由 —— 之後每份報告都會重吵一次 |
| **技術棧** | 每一層用什麼，指回對應的決策 | 選了自己熟的而不是適合的，又不說 |
| **階段路線圖** | Phase 0（地基）、Phase 1…，每階段的目標與**完成條件** | 完成條件寫「功能做完」。要寫成可驗證的：「10k 連線壓測通過」 |
| **待驗證假設與風險** | 還不確定、但架構押在上面的事；各自在哪一階段、用什麼方法驗 | 把假設寫成事實 |

**決策要給推薦，不要給選單。** 跟 `discuss` 的 `@but` 規則一樣：各有道理時講清楚取捨、給推薦與理由。
使用者要的是一個有主見的提案讓他挑錯，而不是一張讓他自己研究的比較表。

### 4. 討論

寫好草稿後跟使用者說「方向草稿產好了」，然後停下來。使用者用 `@ask` / `@but` 標在 `architecture.md` 裡，照 `discuss` skill 處理（討論檔放 `docs/template/discuss/kickoff/architecture.md`）。

收斂的結論寫回 `architecture.md` 正文。**kickoff 階段的討論結論不用寫進 `decisions.md`** —— 方向還沒核准，談不上「偏離」。`decisions.md` 從核准之後才開始記。

### 5. 核准

**使用者明確說「核准」「就這樣」「可以開始」才算。** 「看起來不錯」「嗯」不算 —— 不確定就問一句「方向可以定案了嗎？」

核准後依序做（都是文件，不必再問）：

1. `architecture.md` 頂端狀態改成「已核准（日期）」
2. 填 `CLAUDE.md` 的 `{{}}` 欄位：專案是什麼、硬約束、語言慣例、技術棧、常用指令、架構改動的範圍。刪掉檔頭那段「這份是通用版」的說明
3. 依技術棧，從 `.claude/skills/code-style/` 複製出本專案的規範（例如 `backend-style`、`frontend-style`），把通用原則留下、填入語言特有的部分。**可以延到第一次寫該層程式前**，但不能晚於那時
4. `README.md` 寫專案入口與「接續前必讀」的第一版
5. 寫 `000001 - Phase 1 任務拆解`（規劃型報告，見 `plan-report` skill），告訴使用者「報告產好了」，停下來

## 需要動手實驗才能決定的事

有些選型不跑一下不知道（某個函式庫撐不撐得住、某個 API 的行為）。

- **先問使用者**要不要做實驗，說明要回答什麼問題、大概花多久
- 實驗程式放 `docs/template/spike/<主題>/`（不進版控），**不是**專案程式碼的起點
- 結論寫回 `architecture.md` 的對應決策，附上量到的數字
- 如果實驗量太大（要壓測、要建環境），就把它寫成「待驗證假設」，排進 Phase 0 或 Phase 1 的第一份報告

## 禁忌

| 不要 | 為什麼 |
|---|---|
| 方向還沒核准就建專案骨架、`npm init`、裝套件 | 那些都是技術選型決定，偷跑等於替使用者決定了 |
| 訪談只在對話裡進行 | 回答會很長、對話會被壓縮，訪談結果沒有留下來 |
| 一次問三十題 | 使用者會疲勞、隨便答 |
| 問題不附推薦 | 把思考工作丟回去 |
| 把使用者的模糊回答自己補成具體數字 | 你補的數字會變成架構的地基，而那不是他說的 |
| 硬約束沒有數字 | 「要快」無法拿來否決任何設計 |
| 不寫「不做什麼」 | 範圍會在每一份報告裡悄悄長大 |
| 自己判斷討論收斂了就標「已核准」 | 核准是使用者的動作 |
