Phase 2 新增的核心元件與 WebSocket 二進位契約如下：

| 概念 / 端點 | 後端 (`com.demo.chat`) | 前端 (`frontend/src`) | 協定與行為說明 |
|---|---|---|---|
| WebSocket 連線端點 | `/ws/chat`（因 `context-path: /api`，完整路徑為 `ws://localhost:8080/api/ws/chat`） | `new WebSocket('/api/ws/chat')`（透過 Vite Proxy `ws: true` 轉發） | 建立全雙工長連線，且前端必須設定 **`ws.binaryType = 'arraybuffer'`** |

## 二、對既有功能的衝擊與破壞性風險

- **資料遷移**：沒有。
- **相容性**：
  - `proto/demo/chat/chat.proto` 保持不變。
  - Phase 1 的 `GET /api/messages` 與 `POST /api/messages` 完整保留！新分頁打開時依然先呼叫 `GET /api/messages` 載入歷史訊息，接著建立 WebSocket 長連線接收即時廣播（REST 與 WebSocket 完美互補）。
- **已知風險**：
  1. **多執行緒同時對同一個 `WebSocketSession` 呼叫 `sendMessage` 會拋出 `IllegalStateException`**：標準 Jakarta WebSocket `RemoteEndpoint.Basic` 的同步發送不是執行緒安全的；在 `000008` 中會教你使用 `ConcurrentHashMap.newKeySet()` 管理 Session 並在發送時對單一 Session 加鎖（或使用 Spring `ConcurrentWebSocketSessionDecorator`）。
  2. **忘記設 `ws.binaryType = 'arraybuffer'`**：瀏覽器 `new WebSocket(url)` 預設的 `binaryType` 是 `'blob'`！如果沒改成 `'arraybuffer'`，`event.data` 拿到的是 `Blob` 物件，丟進 `new Uint8Array(event.data)` 會直接變成空陣列 `0 bytes`。這點會在 `000009` 重點教學。

## 三、替代方案與取捨

### A. 後端 WebSocket 實作方式：原生 `BinaryWebSocketHandler`（★ 建議） vs STOMP over WebSocket (`@MessageMapping`)

- **方案甲（★ 建議：繼承 Spring `BinaryWebSocketHandler` 直接收發 `BinaryMessage`）**：
  - **優點**：
    1. **100% 純 Protobuf 二進位幀**：每一個 WebSocket Frame 的 Payload 就是純粹的 `ChatMessage` 二進位 bytes，沒有任何外層文字標頭包裝。
    2. 最能學到底層 `ByteBuffer` ↔ `ChatMessage.parseFrom()` 與瀏覽器原生 `WebSocket` (`ArrayBuffer`) 的直接對話。
- **方案乙（使用 STOMP 子協定 `Spring Messaging`）**：
  - **為什麼排除**：STOMP 會在每個封包外面包一層文字 Header（如 `SEND\ndestination:/app/chat\n\n...`），前端還得額外裝 `@stomp/stompjs` 套件，違反本專案「輕量、0 多餘文字包裝、直接操作底層二進位」的教學初衷。

### B. 歷史訊息載入策略：沿用 Phase 1 `GET /api/messages` + WebSocket 即時推播（★ 建議） vs 連上 WebSocket 時由後端主動推播 1,000 筆

- **方案甲（★ 建議：畫面初始化時呼叫 Phase 1 的 `GET /api/messages` 拉取歷史，WebSocket 專職傳送即時新訊息）**：
  - **優點**：
    1. 這是業界 IM 系統最標準的架構（HTTP 負責分頁/歷史拉取，WebSocket 負責即時增量事件），讓你在 Phase 1 寫好的 `fetchHistoryBinary()` 繼續發揮最大價值。
    2. WebSocket 雙向只傳單筆 `ChatMessage`，型別單純一致。
- **方案乙（廢棄 HTTP API，連上 WebSocket 第一幀推 `ChatHistoryResponse`、後續推 `ChatMessage`）**：
  - **為什麼排除**：同一個 WebSocket 通道混傳兩種不同 Protobuf Message 型別，就必須額外修改 `.proto` 增加一層 `Oneof / Envelope` 外殼，徒增複雜度。
