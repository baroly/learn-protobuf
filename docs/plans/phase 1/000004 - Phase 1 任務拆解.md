## 二、對既有功能的衝擊與破壞性風險

- **資料遷移**：沒有（記憶體儲存，每次重啟歸零）。
- **相容性**：直接沿用 Phase 0 的 `proto/demo/chat/chat.proto`，**不需修改 `.proto` 欄位**。
- **既有行為的改變**：
  - 後端保留 Phase 0 的 `ChatProtoSerializationTest`，新增 Web 與 Store 層。
  - 前端 `App.vue` 將從 Phase 0 的靜態驗證畫面升級為可與後端互動的 HTTP 聊天室畫面。
- **已知風險**：
  1. **瀏覽器 `fetch` 傳送 `Uint8Array` 的型別相容性**：TypeScript 6.x 的 DOM 型別中，`Uint8Array` 傳給 `fetch` 的 `body` 時，若 `Uint8Array<ArrayBufferLike>` 與 `BodyInit` 型別檢查過嚴，可用 `new Uint8Array(bytes)` 或 `bytes.slice()` 處理（將於 `000006` 詳解）。
  2. **忘記把 `response.arrayBuffer()` 轉成 `Uint8Array`**：`protobufjs` 的 `decode()` 只收 `Uint8Array`，不直接收 `ArrayBuffer`，將在 `000006` 的 `chatApi.ts` 封裝中統一轉換。

## 三、替代方案與取捨

### A. 拆成 2 份報告：後端 `000005` + 前端 `000006`（★ 建議） vs 拆成 3 份（Store 獨立一份）

- **方案甲（★ 建議：拆成 `000005` 後端 + `000006` 前端共 2 份）**：
  - **優點**：`ChatMessageStore` 邏輯非常精煉（約 40 行程式碼），與 `ProtobufHttpMessageConverter`、`ChatController` 放在同一份報告 `000005` 裡，可以一氣呵成從資料儲存寫到 `MockMvc` HTTP 測試，體感最連貫。
- **方案乙（把 `ChatMessageStore` 單獨拆成一份報告）**：
  - **為什麼排除**：Store 單獨一份只有一個類別，粒徑太碎，多一次報告核准往返。

### B. 開發期前端連後端方式：Vite Server Proxy `/api`（★ 建議） vs 後端 `@CrossOrigin` CORS

- **方案甲（★ 建議：在 `vite.config.ts` 配置 `server.proxy` 將 `/api` 轉發至 `http://localhost:8080`）**：
  - **優點**：
    1. 前端直接呼叫相對路徑 `fetch('/api/messages')`，瀏覽器視為同源請求（Same-Origin），**不會觸發額外的 `OPTIONS` Preflight 預檢請求**，在 DevTools Network 面板看 `application/x-protobuf` 封包最乾淨！
    2. 到了 Phase 2 接 WebSocket (`/ws/chat`) 時，同樣在 `vite.config.ts` 加一行 `ws: true` 就能無縫代理。
- **方案乙（前端寫死 `http://localhost:8080/api/messages` + 後端設定 CORS）**：
  - **為什麼排除**：因為自訂了 `Content-Type: application/x-protobuf`（非簡單請求 Simple Request），瀏覽器每次 `POST` 前都會先發一個 `OPTIONS` 預檢請求，干擾 Network 面板觀察，且後端需多寫 CORS 配置。
